    fault

    builtin:fault#

    Simulates a bad network on one or more containers: delay, jitter, packet loss, corruption, duplication, reordering, and bandwidth caps, set together in one with block. Use it to see how your app handles a slow or unreliable dependency. It works underneath builtin:route and the kevin proxy, so it impairs a container’s traffic no matter how that traffic gets there.

    Like other steps, you target containers through needs. With no containers set, a fault step affects every container its needs entries resolve to. That covers the common case: a builtin:container step reports exactly one container, so there’s nothing to narrow:

    backend: {uses: "builtin:container", with: {image: "myapp/backend"}}

backend_fault: {
    uses:  "builtin:fault"
    needs: ["backend"]
    with: {
        delay_ms:     200
        loss_percent: 10
    }
}

    A builtin:kind cluster reports one container per node - name a workers key (see that reference page) to fault it individually, or two of them at once:

    cluster: {uses: "builtin:kind", with: {workers: {worker_a: {}, worker_b: {}}}}

worker_fault: {
    uses:  "builtin:fault"
    needs: ["cluster"]
    with: {
        containers:   ["worker_a", "worker_b"]
        loss_percent: 25
    }
}

    containers matches the literal name you already declared - worker_a in cluster’s own workers map, or (for a single-container step like backend above) that step’s own name as a fallback: containers: ["backend"] works too, even though builtin:container itself reports "kevin-demo-backend". Cross-scope works the same way needs already does: needs: ["setup.registry"], and "registry" still resolves as that step’s fallback name.

    FieldTypeDefaultDescription
    containers[...string]-Narrows which container this fault impairs, by name. Unset means every container every needs entry resolves to - a builtin:kind cluster with no other needs entries, say, faults every node identically. A name matches either a container’s own name (as reported by its step - see the reference doc for how each plugin determines it), or, when a needs step manages exactly one container, that step’s own name as a fallback: "cache" works whether the step reporting it is a builtin:container step or the one worker of a builtin:kind cluster.
    interfacestring-The network interface inside the target container to impair. Empty picks the relay’s own default ("eth0").
    delay_msint & >0-The fixed one-way delay added to every packet, in milliseconds.
    jitter_msint & >=0-The random variation applied around delay_ms, in milliseconds. Only meaningful alongside delay_ms.
    loss_percentfloat & >0 & <=100-The percentage of packets dropped.
    corrupt_percentfloat & >0 & <=100-The percentage of packets corrupted (a single bit flipped).
    duplicate_percentfloat & >0 & <=100-The percentage of packets duplicated.
    reorder_percentfloat & >0 & <=100-The percentage of packets reordered ahead of delay_ms. Only meaningful alongside delay_ms.
    rate_kbitint & >0-Caps the interface’s throughput, in kilobits/second.

    At least one impairment field must be set; Up rejects an otherwise-empty with block. A containers entry naming nothing any needs step reports is an Up-time error - as is an empty with block when no needs step reports any container at all.

    Kind: action. A fault step deploys nothing itself: it tells the relay how to treat a namespace another step already created. It has no Down - the engine clears every fault it applied at teardown on its own, independent of whether a step’s plugin implements Down at all.

    Idempotent: re-Up-ing with a changed config replaces each netem qdisc’s parameters, matching how Linux’s own tc qdisc replace behaves.
